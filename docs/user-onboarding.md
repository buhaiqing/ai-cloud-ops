## 2. 试用任务清单（最少 3 选 5）

每条都有"完成定义"，**不要发模糊任务**。

### T1 — 看 1 个真实告警的 AI 诊断 ⭐⭐⭐

**前置**：staging 已配 CloudMonitor webhook，账号下至少有 1 条 critical 告警。

**步骤**：
1. 登录 dashboard
2. Alerts 页面找到任意一条 severity=critical 的告警
3. 点开看详情，确认 AI 分析在 60 秒内出来
4. 阅读 root_cause + recommendations

**完成**：能用自己的话复述"这个告警是 X 资源 / Y 原因 / 建议 Z 操作"。

**反馈问题**：
- AI 诊断花了多久？（看页面底部 `latency_ms`）
- 根因写得对吗？哪个细节不对？
- 推荐操作你敢直接批吗？为什么？

### T2 — 走 1 次 HITL 审批流程 ⭐⭐⭐

**前置**：T1 看到一条带 recommendations 的告警。

**步骤**：
1. 在告警详情页点 "Approve" 一条 recommendation
2. 系统会先弹 dry-run（"将执行 X，预估影响 Y，回滚策略 Z"）
3. 确认 → 看 exec plan 进入 `running` → 等结果（成功 or 自动回滚）
4. 切到 Executions 页面看 audit log

**完成**：亲眼看到 1 次 plan → approve → execute → audit 的完整链路。

**反馈问题**：
- dry-run 信息够不够决定"批还是不批"？
- 哪个环节最不放心？（批准 / dry-run / 执行 / 回滚）
- 想看但没看到的字段？（比如"会改什么" / "为什么建议" / "成本预估"）

### T3 — 测 1 次故意失败的回滚 ⭐⭐

**前置**：启用 `AICO_ROLLBACK_ENABLED=true` 重启 backend（参考 staging runbook §2.3）。

**步骤**：
1. 选 1 个**无关紧要**的测试 ECS 实例（建议先打 tag `aico-managed=true`）
2. 触发 1 个 "restart ECS" 的 plan
3. **在 plan 执行前**，手动把 ECS 状态改成 running（让 restart 失败）
4. 看 audit log 是否自动回滚 + plan 状态变成 `rolled_back`

**完成**：见过至少 1 次自动回滚路径。

**反馈问题**：
- 回滚触发时机合理吗？
- 回滚动作的"反向操作"够不够清晰？
- 你愿意在生产用 `AICO_ROLLBACK_ENABLED=true` 吗？

### T4 — 改 1 条告警规则 ⭐⭐

**步骤**：
1. Rules 页面新建 1 条阈值规则（如：CPU > 80% 持续 5 分钟告警）
2. 编辑它（改阈值 / 改通知渠道）
3. 删掉它

**完成**：CRUD 流程走完 1 遍。

**反馈问题**：
- 规则表单字段够不够？少什么？（例：抑制规则 / 分组 / 升级策略）
- 编辑/删除的二次确认够清晰吗？

### T5 — 体验 WebSocket 实时推送 ⭐

**步骤**：
1. 打开 dashboard Alerts 页面（保持登录）
2. 在另一个浏览器窗口触发 1 条 webhook（开发者工具或 curl）
3. 看新告警是否**不刷新页面**就出现

**完成**：看到 ≥ 1 条新告警自动出现，且连接稳定不掉。

**反馈问题**：
- 推送延迟体感多少秒？
- 推送频率合理吗？（会不会太密 / 太稀）
- 断线后能自动重连吗？

## 3. 不让用户做的事（重要！）

| 不能 | 原因 |
|---|---|
| ❌ 用 staging 账号对生产资源做"执行"操作 | dry-run 已过滤非白名单操作，但执行类仍要走 approval；staging 账号只对测试资源打 `aico-managed=true` tag |
| ❌ 把 `.env` 凭证分享出去 | staging 凭证给到 OSS / 第三方 = 阿里云账单风险 |
| ❌ 关掉 staging 的 webhook 集成 | 会导致其他人试用看不到告警 |
| ❌ 修改 staging DB schema | 会破坏其他用户的试用；如需改 → 反馈进 §4 表 |

## 5. 试用结束后的同步会（30 分钟）

每个用户跑完做一次 30 分钟视频同步，按下面流程：

```
[0:00-0:05] 试用期间遇到过什么问题？
[0:05-0:10] Q1-Q10 答案先快速过一遍
[0:10-0:20] 让用户操作 dashboard，远程看他在哪里犹豫
[0:20-0:25] 关键追问：
            - "你愿意把 staging 这套用到生产吗？为什么不？"
            - "你愿意为哪个功能付钱？"
            - "如果只能留 3 个特性，留哪 3 个？"
[0:25-0:30] 下一步（产品方向 / 用户试用扩展 / bug 修复）
```

**关键判断**（5 用户答完会得到）：

| 答 → | 决策 |
|---|---|
| ≥ 3 人 Q1 ≥ 7 | M4 主路径：打磨 AI + HITL，不转方向 |
| ≥ 3 人 Q1 ≤ 4 | M4 主路径：先做 X（看 Q3 最高频特性） |
| ≥ 3 人 Q9 = "完全不接受" | 必须做 BYOK（自带 LLM key）或 on-prem |
| ≥ 3 人 Q10 = "$0" | OSS 路线，不做 SaaS |
| ≥ 3 人 Q10 = "$50+" | SaaS 路线，启动多租户（M4-6） |

## 6. 用户招募建议

| 来源 | 优点 | 缺点 | 推荐 |
|---|---|---|---|
| 内部 Ops 团队 | 熟悉业务，反馈深 | 人数少，可能客气 | ✅ 主选 |
| 阿里云 MVP / 社区 | 视角多元，敢喷 | 不熟你的运维栈 | ✅ 至少 1 个 |
| 朋友公司运维 | 中立，不会捧场 | 协调成本 | ✅ 1-2 个 |
| Reddit / V2EX | 量大，敢说 | 噪声多，需要筛选 | ⚠️ 备用 |
| Twitter / X OSS 圈 | 影响大 | 容易被喷"玩具" | ❌ 试用阶段不要 |

**5 人推荐组合**：3 内部 + 1 外部运维 + 1 阿里云 MVP。
